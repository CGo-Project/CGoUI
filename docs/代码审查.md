# CGoUI 开源发布前审查

## 结论

**Request Changes — 暂不建议直接将仓库切换为 Public，也暂不建议以当前状态发布新的公共 NPM 版本。**

当前构建与打包链路本身健康：main CI 已通过 `npm ci`、生产构建、包内容检查、`npm pack --dry-run` 与 smoke test；本次阻塞项主要来自开源许可、第三方素材、历史隐私与公开 API 安全边界，而不是编译问题。

## 🔴 阻塞问题

### 1. `examples/bjsubway` 包含权属未说明的第三方品牌内容与图片素材

`examples/bjsubway/index.html` 明确模拟北京地铁官方网站内容，包含“北京市地铁运营有限公司”版权信息、服务热线、备案信息、微博链接以及多张本地宣传图、新闻图和服务质量承诺图片。`THIRD_PARTY_NOTICES.md` 当前只声明 Lit / React 等代码依赖，没有说明这些图片、文案、站点品牌或其再分发许可。

开源前必须二选一：

- 删除/替换为 Central Go 自制的演示图片、虚构文案与通用品牌；或
- 确认拥有公开再分发所需的授权，并在仓库中为这些素材增加明确的版权、许可范围、来源与“不属于 Apache-2.0 授权范围”等说明。

仅把 `examples/` 排除在 NPM 包之外不能解决 GitHub 仓库公开后的再分发问题。

### 2. 核心图标集中存在 `bjsubway` 品牌图标，授权边界未说明

`src/icons/icons.js` 将 `bjsubway` 放在“品牌标识 (Brand Icons)”下；该文件会进入 NPM 发布包，并被打进 `dist/cgo-ui.js`。如果该图形属于第三方商标/品牌标识，应在公开发布前确认使用及再分发边界。更稳妥的开源方案是从通用组件库核心中移除第三方官方品牌图标，改用通用轨道交通图标；如确需保留，则增加独立的商标/品牌声明，且不要暗示 Apache-2.0 授予第三方商标使用权。

### 3. 第三方许可说明与实际构建方式不一致

`scripts/build.mjs` 对 vanilla `src/register.js -> dist/cgo-ui.js` 配置 `external: []`，因此 Lit 运行时会进入 vanilla bundle；但 `THIRD_PARTY_NOTICES.md` 当前写着这些 peer dependencies “不把这些 peer dependency 打包进 dist”。这与实际构建配置不一致。

发布前应：

- 准确区分 vanilla bundle 中被打包的 Lit 与 React 适配入口中 external 的依赖；
- 核对生成 bundle 是否保留 Lit 的法定版权/许可注释；
- 在发布包中提供满足被打包依赖许可证要求的完整归属/许可文本，而不是仅说明“安装后的依赖目录可查看”。

## 🟡 建议在公开前修复

### 4. GitHub 当前未识别出 Apache-2.0

仓库元数据当前返回 license `NOASSERTION / Other`。`LICENSE` 文件前面先放了一段 Apache 使用声明，再拼接完整许可证正文；建议将 `LICENSE` 恢复为规范的 Apache-2.0 原文，版权声明保留在现有 `NOTICE` 中。公开后应确认 GitHub 页面能正确显示 `Apache-2.0`。

### 5. Git 历史包含贡献者真实邮箱

历史提交中存在贡献者的真实邮箱地址，而较新的提交已改用 GitHub noreply 地址。仓库一旦公开，Git 历史也会公开。如果这些真实邮箱本来就允许公开，可保持；如果不希望被长期公开，应在切 Public 前征得贡献者意见并完成历史重写，再通知所有协作者重新 clone/rebase。

### 6. `SECURITY.md` 没有可执行的私密报告入口

当前只写“通过项目维护者约定的私下渠道”，但公开用户并不知道该渠道是什么。建议明确提供 GitHub Private Vulnerability Reporting（若启用）或专用 security 邮箱，并说明支持版本与响应预期。

### 7. 公开 API 存在可信 HTML / XSS 边界不清晰

`src/shim/cgo-global.js` 的 `showHelpModal()` 将 `title`、`subtitle`、`iconPath`、`content` 等拼接后写入 `innerHTML`；`src/components/toolbar-select.js` 使用 `unsafeHTML(opt.innerHTML)`。这在“调用方只传仓库内静态可信 HTML”时可以工作，但外部开发者若把接口数据、URL 参数或用户输入直接传入会形成 DOM XSS 风险。

建议：普通文本字段统一转义；确实需要 HTML 的字段显式命名为 `contentHtml` / `trustedHtml` 并在 API 文档中加安全警告；`unsafeHTML` 尽量改成安全 DOM 克隆或受控白名单。

### 8. `cgo-captcha` 不能作为真正的安全验证码

实现完全在客户端生成题目和答案，答案还会通过属性/事件暴露。应在 README/组件文档中明确标注“仅用于 UI/交互演示，不得用于登录、注册、风控或反机器人安全校验”，避免开源用户误用。

### 9. 发布包元数据与类型声明仍可提升

`package.json` 缺少 `repository`、`homepage`、`bugs`、`keywords` 等常见公共包元数据；`src/index.d.ts` 与 `src/react.d.ts` 的组件类型目前几乎全部是 `any`。这些不阻塞开源，但会明显影响 npm/GitHub 可发现性和 TypeScript 用户体验。

### 10. 公开仓库安全配置待开启/确认

当前 GitHub API 返回 Dependabot alerts 未启用；分支保护设置因当前集成权限无法读取，无法确认是否已强制 PR + Review + CI。公开前建议至少确认：main 分支保护、Dependabot alerts、安全更新、Secret Scanning/Push Protection（账户/计划可用时）以及 NPM 2FA/维护者权限边界。

### 11. `.gitignore` 建议补充环境文件规则

当前已忽略 `.npmrc`，但没有 `.env` / `.env.*`。建议增加 `.env`、`.env.*` 并按需保留 `!.env.example`，降低未来贡献者误提交凭据的概率。

## ✅ 已通过的项目

- 当前 `main` 对应提交已完成 CGoUI CI，安装、构建、打包检查和 smoke test 全部成功。
- CI 的 `npm ci` 当前报告 0 个已知漏洞。
- `scripts/check-package.mjs` 会执行 `npm pack --dry-run` 并验证必要发布文件；当前 CI 报告 49 个文件进入发布包。
- `.npmignore` 与 `package.json.files` 已排除 `examples/`、`legacy/`、`docs/` 等非 NPM 运行时内容。
- `README.md` / `CONTRIBUTING.md` 已明确普通贡献者走 PR、正式 NPM 发布由维护者执行。
- Apache-2.0 正文、NOTICE、THIRD_PARTY_NOTICES、CHANGELOG、SECURITY 等基础治理文件均已存在。

## 建议发布顺序

1. 先处理 `examples/bjsubway` 图片/文案/品牌标识的权属与替换。
2. 处理核心 `bjsubway` 品牌图标的商标/许可边界。
3. 修正 Lit 打包事实与 THIRD_PARTY/NOTICE 许可文本。
4. 规范化 LICENSE，使 GitHub 正确识别 Apache-2.0。
5. 决定是否保留历史提交中的真实邮箱；如需移除，必须在 Public 前重写历史。
6. 补 SECURITY 私密报告入口、可信 HTML 安全警告、Captcha 安全说明和 `.env` ignore。
7. 再跑一次 CI / `npm run release:check`，确认 package 内容。
8. 配置 main 分支保护与 GitHub 安全功能，再将仓库切换为 Public。
9. 最后由维护者发布 NPM，并创建对应 Git tag / GitHub Release。
